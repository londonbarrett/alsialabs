# Project management — Design

## Why this exists

A project is the app's unit of coordinated work: it owns tasks, routines, expenses, and people, and almost every other capability hangs off it. The design therefore treats the open project as shared, page-scoped state — one store seeded when the detail area loads, read by every subpage, header, and tab — rather than as props threaded through a component tree or state re-fetched per section. The detail area splits into five subpages (tasks, routines, details, people, expenses) under one persistent header, because all of them are views onto the same project.

The capability also carries the app's heaviest optimistic-state machinery. Tasks, routines, expenses, comments, and membership changes all apply instantly and revert on failure, with each page holding its own store and each mutation owning its toast. The reason is structural: these stores are seeded once per page mount, so `router.refresh()` cannot reach them — every change must travel through optimistic actions that commit the server's authoritative row or discard on error.

Ownership is the authorization boundary. Not the global permission system: membership mutations are guarded by who is recorded on the project, deliberately stricter than the access check that also admits super users. That keeps day-to-day management in the hands of the project's own owners without requiring them to hold global edit permissions.

## Goals

- Split the project detail area into five permissioned subpages sharing one header and one context store.
- Let owners create, view, edit, and delete projects with a required identifying color.
- Make every list and membership mutation optimistic with automatic revert and per-action toasts.
- Enforce ownership-based authorization on membership changes, stricter than super-user access.
- Give owners, collaborators, and assignees appropriate views of tasks, comments, and routines.

## Design

### Subpage navigation and layout

The project detail area is five subpages under `/app/proyectos/[id]`: tasks (the default at the bare route), `rutinas`, `detalles`, `personas`, and `gastos`. Every subpage requires `projects:view`, enforced through `getProjectContext` — a `sessionAction` declaring `permission: projects:view`, layered over a `projectScopedAction` whose `verifyProjectAccess` admits `project_owners`/`project_collaborators`/`super`.

`app/app/proyectos/[id]/layout.tsx:17` calls `getProjectContext` and, before `unwrapResponse`, handles the failures itself: `if (!result.data) notFound()` for an unknown project (404 screen) and `serverError FORBIDDEN` → `forbidden()` for a user without access (403 screen). The successful `ProjectContextDTO` is passed to `ProjectContextProvider`, so the guard and the state seeding happen in the same place.

All subpages share a persistent header — back button, project name, location, status badge — plus a tab navigation highlighting the active subpage. Both the header and the tab hrefs read from the project context store via `useProjectContext`: `components/projects/project-view.tsx:38` reads `project` and `projectId` and derives `basePath` from `projectId` at `:39`, so the displayed title and the tab links always come from the same read and cannot disagree. `ProjectView` accepts no `projectId` or `context` props; there is no second source of truth. `lib/util/unwrap.ts:22` returns `[]` by default for array results, so array-typed actions degrade to empty lists rather than undefined.

### Project creation and the shared form

Owners create projects; the primary owner and super users have full control. A project carries a required color drawn from a fixed palette of exactly 6 swatches with no default selection — submitting without one shows a "color is required" validation error and creates nothing. The color identifies the project on cards and calendar events but is not unique: any two projects may share a color, and the choice is accepted whenever made.

`ProjectForm` (`components/projects/project-form.tsx`) is rendered by both the projects list page and the project detail subpage, and it owns no mutation. It calls its required `onSubmit` prop (`components/projects/project-form.tsx:56`) and maps server field errors onto the inputs; it never imports `createProject` or `updateProject`, so it cannot create a project where an update was intended. It takes no separate `onSuccess` prop and does not await `onSubmit` — `ProjectFormSubmit` is typed `(values: ProjectFormValues) => void`, and closing the dialog belongs to `ProjectDialog`. It declares no result type for `onSubmit`, because nothing inspects a server result on that path. The caller that owns the mutation also owns its toasts, matching `useProjectActions` and the list page's create handler.

The `project` prop only pre-fills fields; it never selects the mutation. That keeps create and edit paths distinguishable by construction: the list page, which sits outside any project context, passes a create handler and no `project`, while editing is reachable only from the details subpage, which passes `onSubmit={updateProject}` to mutate the project context store.

### The projects list page and its store

The list at `/app/proyectos` is permissioned at both ends: `hasPermission` in `app/app/proyectos/page.tsx:12` on the page, and `sessionAction` `permission: projects:view` inside `getProjectsWithDetails`/`getProjects`. Projects render as a card grid — name with a color dot, category, status badge, dates, budget bar, task progress, and the primary owner marked with a crown icon — under a header with a "Portfolio" label, "Projects" title, and subtitle. `getProjectsWithDetails` filters by a `projectOwners` `exists` for non-super users and unwraps with the `[]` fallback; users without `projects:view` receive 403 via `forbidden()`. Clicking a card's title navigates to `/app/proyectos/[id]`, landing on the tasks subpage.

Rows live in a client store created per page visit, never a module-level singleton. `app/app/proyectos/page.tsx` renders `ProjectsProvider` (`components/projects/projects-provider.tsx` — named for what it provides, not the page it serves), which builds the store once per mount with `useState(() => createProjectsStore(projects))` and publishes it through `ProjectsStoreContext` (`stores/projects/projects-store.ts`). The provider does not hydrate itself from changing props: the store is seeded once and mutations reach the client through optimistic actions. Navigating away and back remounts the provider and reseeds from freshly fetched projects.

Consumers read the list through `useProjectsState` (`stores/projects/use-projects-state.ts`), the store's single state hook, which returns `projects`, `pending`, and the derived `pendingIds`. Nothing selects `s.optimistic` or `s.pending` directly, the hook does not alias `projects` under a second name, and `createProjectsStore` attaches no imperative read methods — `useProjectsActions` reads through `store.getState()` via `useOptimisticAction`.

Creating a project is optimistic through `useOptimisticAction` (`stores/use-optimistic-action.ts`): `add` inserts a pending row, then a `commitAction` issues `replaceTemp` to swap in the authoritative server row. Pending rows render as pending rather than as confirmed projects, and on failure the pending action is discarded with an error toast. The signed-in user's owner row (`ProjectOwnerDTO` in `stores/projects/use-projects-actions.ts`, an alias of a `Project` owner) is passed from `app/app/proyectos/page.tsx` through `ProjectsView` (`components/projects/projects-view.tsx`) into `useProjectsActions`, so the optimistic row shows its real owner without reading `useSession`. There is no non-optimistic fallback, because `router.refresh()` cannot reach a once-seeded store. `ProjectDialog` (`components/projects/project-dialog.tsx`) is a single component with no store logic and a required `onSubmit`; the caller owning the mutation owns the optimistic write.

### The project context store

The open project's context is a client store created per detail page — not a singleton, not props. `app/app/proyectos/[id]/layout.tsx` renders `components/projects/project-context-provider.tsx`, which builds the store exactly once per mount with a lazy initializer, `const [store] = useState(() => createProjectContextStore(context))`, and publishes it through `ProjectContextStoreContext` (`stores/project-context/project-context-store.ts`). Reading `ref.current` during render is forbidden by `react-hooks/refs`, so `useRef` + `if (storeRef.current == null)` is not an option and no `eslint-disable` is used to work around it. This is the same construction as every other store provider (`ProjectsProvider`, `InvoiceProvider`, `TimelineProvider`, `ActivityProvider`).

Because the store is seeded at construction it has no "not yet seeded" state: no consumer needs a null guard, and seeding is never repeated from an effect. It holds exactly one project — the route supplies the identity — so `projectContextReducer` takes no key. Re-rendering the layout does not rebuild or re-seed it; navigating from project A to project B remounts the provider with B's context, leaving nothing of A observable.

Every mutation is a `ProjectContextAction` (`stores/project-context/project-context-reducer.ts:8`) applied through `createOptimisticStore`, so client state is never re-read from the server: `patchProject`, `addOwner`, `addCollaborator`, `removeOwner`, `removeCollaborator`. Membership actions are no-ops — returning the identical state reference — when the user is already present or absent, preserving referential stability for memoized consumers.

Consumers read through `useProjectContextState()` (`stores/project-context/use-project-context-state.ts`), which returns one object: `project`, `projectId`, `owners`, derived `primaryOwner`/`additionalOwners`, `collaborators`, `members`, `categories`, `currentUserId`, `isCurrentUserAdmin`, and the role flags `isOwner`/`isPrimaryOwner`/`isCollaborator`. The hook takes no `initialContext` argument, never returns the raw context, and exposes no `permissions` or permission-derived capability — a component composes `isOwner && useHasPermission("projects:edit")` itself, calling `useHasPermission` unconditionally at the top level of render rather than behind a conditional. Mutating hooks (`useProjectActions`, `useProjectPeopleActions`) read `projectId` from the same hook and throw if called outside a `ProjectContextProvider`, naming it in the error. Inside the project area `project` is never null, so no guard or loading placeholder is needed.

### Project details, editing, and deletion

The details subpage (`/app/proyectos/[id]/detalles`) shows a `Card` of project info with entries in a fixed order — primary owner, category, color, location, start date, end date, budget, description — where the color entry is a swatch with its localized color name, and edit and delete buttons sit in the card footer.

Edit opens `ProjectDialog` with current values pre-filled, including the current color selected among the six swatches. On submit the project is patched optimistically in the project context store, then the authoritative row returned by the server is committed on top so server-side normalization wins; if the server rejects the change, the optimistic patch is discarded and an error toast is shown.

Delete is limited to the primary owner or a super user: a styled confirmation dialog shows the project name, and confirming deletes the project and redirects to the projects list. Status can also be changed inline from a dropdown on the details subpage, taking effect immediately without a page reload.

### Ownership model and the people UI

Projects support multiple owners and collaborators. The primary owner has full control; owners manage collaborators and tasks; collaborators view the project and comment on tasks. Collaborators cannot see the project in the list or open its subpages — only owners can access project details.

The people subpage (`/app/proyectos/[id]/personas`) is composed from `components/projects/project-people.tsx`, `components/projects/member-pill.tsx:1`, and `components/projects/user-invite-input.tsx:45`. `MemberPill` renders a `size-8` `Avatar` with `initials`, the member's name over their email at `text-xs text-muted-foreground`, and an `X` remove button — and the email only renders as a second line when the member has both a name and an email, so a member without a name still shows their email exactly once, never twice or never. User search in the invite combobox is debounced 300ms via `hooks/use-debounced.ts:3` `useDebounced`.

Controls follow role: the primary owner sees a "Co-owners" section with the search combobox and a remove button on each non-primary owner, and can transfer primary ownership to another owner (the page refreshes after transfer); a non-primary owner sees no co-owner controls at all; any owner sees a "Collaborators" section with add/remove controls; a collaborator sees neither add/remove control.

Membership changes apply optimistically to the project context store through `useProjectPeopleActions` (`stores/project-context/use-project-people-actions.ts:48`) and do not depend on `router.refresh()`, because the context store is seeded once per mount. Adding or removing a member pends the action and renders the result immediately; a server rejection discards the pending action and shows the server's error. Each mutation reports exactly one toast: a translated error (`useActionError` over the `errors` namespace) for a `serverError`, or a success toast (`projects.ownerAdded`/`ownerRemoved`/`collaboratorAdded`/`collaboratorRemoved`) for `data`. Each removal is its own action (`removeOwner`/`removeCollaborator`) dropping the user from only that list, mirroring the separate `removeProjectOwner`/`removeProjectCollaborator` server actions. `UserInviteInput`'s `onSelect` receives the whole `UserOptionDTO` (`components/projects/user-invite-input.tsx:27`), not just an id, so the reducer can render the new member's name, email, and image before the server responds; a rejected invite (`ALREADY_OWNER` or `ALREADY_COLLABORATOR`) removes the pill again and shows the server's error, and a rejected removal makes the pill reappear with the server's message.

### Membership actions and authorization

Membership mutations live in `actions/project-people.ts` as safe actions built with `projectScopedAction` (`lib/safe-action.ts:141`), taking `{ projectId, userId }` and declaring `revalidate: ["/app/proyectos/:projectId"]` — so a commit on project `abc` calls `revalidatePath("/app/proyectos/abc")` from the `:projectId` template. They declare no `metadata.permission`: the ownership check is the authorization, which is what lets a project owner without a global `projects:edit` permission manage members.

Failures come back as codes through `returnActionError` — `FORBIDDEN`, `NOT_FOUND`, `ALREADY_OWNER`, `ALREADY_COLLABORATOR`, `CANNOT_REMOVE_PRIMARY_OWNER`, `MUST_BE_OWNER` — declared in `actions/error-codes.ts` and translated from the `errors` namespace, never as interpolated server strings.

The guards are deliberately stricter than `ctx.isProjectOwner`, which `verifyProjectAccess` also grants to super users. `addProjectOwner`, `removeProjectOwner`, and `transferPrimaryOwner` require the caller to be the primary owner, compared against `projectsTable.primaryOwnerId`: a non-primary owner gets `FORBIDDEN`. `addProjectCollaborator` and `removeProjectCollaborator` require the caller to appear in `projectOwnersTable`. A super user who is not recorded on the project is therefore rejected with `FORBIDDEN` on every membership mutation. `removeProjectOwner` on the primary owner's own id returns `CANNOT_REMOVE_PRIMARY_OWNER`; `transferPrimaryOwner` targeting a non-owner returns `MUST_BE_OWNER`; a collaborator added as owner returns `ALREADY_COLLABORATOR`, and an owner added as collaborator returns `ALREADY_OWNER`. The reads `getProjectOwners` and `getProjectCollaborators` are `sessionAction`s with `permission: projects:view` and input `{ projectId }`, and `getProjectContext` (`actions/projects.ts:541`) calls them with an input object, unwrapping through `unwrapResponse`.

### User search and invite

The invite combobox (`components/projects/user-invite-input.tsx`) searches existing users and offers an invite option, backed by the `searchUsers` safe action — a `sessionAction` with `permission: projects:view` and schema `SearchUsersSchema: {query, excludedIds?}` that `ilike`-searches `usersTable` on `name`/`email` across all roles with `limit 20`. Results appear as the user types, debounced 300ms via `useDebounced`, as `UserOptionDTO` from `searchUsers` `data`. Users already associated with the project are excluded client-side via `excludedIds` — `allMemberIds` collected in `project-people.tsx:28` — and the cross-role guards sit in the actions themselves: `addProjectOwner` blocks a collaborator (`ALREADY_COLLABORATOR`) and `addProjectCollaborator` blocks an owner (`ALREADY_OWNER`) at `actions/project-people.ts:141`/`215`. Selecting "Invite" triggers the invite without a loading spinner; a cross-role duplicate surfaces as the `ALREADY_OWNER`/`ALREADY_COLLABORATOR` toast.

### Task management

Tasks live on the tasks subpage, the default project subpage, inside a Card with a `ListTodo` icon in the header. `app/app/proyectos/[id]/page.tsx` mounts `ProjectTasksProvider` with the `getTasks` result and `TasksCard` reads `useProjectTasksState()` — a page-scoped store, because a failed mutation must discard only its own pending action so concurrent mutations cannot overwrite each other. Create, edit, delete, status change, and priority change all apply optimistically, show the global loading indicator during the server request, and confirm with a success toast.

Owners get the full dialog — name, description, cost, status, assignee (a dropdown of project owners and collaborators), priority, and due date — where the priority dropdown defaults to no priority and the due date field defaults to empty. Both are optional: a task can be created with neither, and the Due Date column then shows an em dash. Priority accepts `urgent`, `high`, or nothing; it changes optimistically from an inline dropdown on the row. The due date is a datetime set from a date field plus an optional time field, rendered in the Due Date column with its time when set.

Status flows differently by role. Owners pick any status from the inline dropdown, including `cancelled` — which is how a task is cancelled, and selecting any active status reopens it with its previous data intact. Collaborators get `TaskStatusSelect` restricted to `blocked` and `in_review`, and see no "Add Task" button and no task action menus. An assignee in My Tasks gets collaborator-level restrictions (`in_progress`, `blocked`, `in_review`) — never `done` or `cancelled`. A cancelled task is read-only for non-owners: its status renders as a badge with no dropdown, it shows no "Overdue" badge and no red due-date text even when past due, and it is excluded from project task progress, which computes done / (total − cancelled) so cancelled tasks contribute to neither the numerator nor the denominator.

Overdue is otherwise shown in the Due Date column as an "Overdue" badge with red due-date text for any task not in `done` or `cancelled` with a past due date; the indicator disappears as soon as the task reaches `done` or `cancelled`. Each row shows a comment count next to a `MessageSquare` icon — always visible including 0, and always a number. Double-clicking anywhere on a task row opens the comments panel as a slide-over Sheet, as does clicking the comment count button.

### Task comments

Owners, collaborators, and task assignees — including an assignee who is not a project member — can hold conversations on tasks, displayed in a slide-over Sheet. Only the comment author or project owners can delete a comment, and only the author can edit their own.

Comment operations are safe actions in `actions/task-comments.ts` — `getTaskComments`, `createComment`, `updateComment`, `deleteComment`, each a `sessionAction` taking an input object with its schema in `actions/schemas/task-comment.ts`, returning failures as codes via `returnActionError` — and they run optimistically with the global loading indicator and success toasts. Comments live in the page's own store keyed by task id: the project tasks store on the project subpage, the my-tasks store on My Tasks. They are loaded when the panel opens.

A comment mutation adjusts the owning task's `commentCount` in the same store action, so a rejected comment rolls its count back with it and the count cannot drift from the list; loading comments reconciles `commentCount` to the fetched length. No controller reports count changes upward through a callback — the count moves with the comment in the store action, so `MyTasksList` receives no `onCommentCountChange`.

The panel itself is presentational and shared: `TaskCommentPanel` (`components/common/task-comment-panel.tsx`) is a dumb component taking comments plus callbacks and owning only the draft text and scroll position, and each row is `TaskCommentBubble` (`components/common/task-comment-bubble.tsx`), which owns its own edit-in-place state — the edit draft, Save/Cancel — and receives `onEdit`/`onDelete`, so editing one comment cannot re-render the panel's draft state. Each domain supplies its own controller over the panel: `ProjectTaskCommentsPanel` (`components/projects/project-task-comments-panel.tsx`) and `MyTaskCommentsPanel` (`components/my-tasks/my-task-comments-panel.tsx`), each reading and writing its own store — markup exists once, while loading, fetching, and mutations stay per domain.

The panel header shows the task name with the description below in muted text; comments render chronologically with the author's avatar, name, relative timestamp, and content, with "(edited)" appended after the timestamp once edited, and a refresh button in the header re-fetches the list with a spinner. Sending (Send button or Enter) adds the comment optimistically with a success toast and increments the task row's count. Hovering your own comment reveals a pencil icon that turns the content into a textarea with Save (or Enter) and Cancel (or Escape); a successful save shows "(edited)", a discard restores the original. Other users' comments show no edit icon, and the delete (trash) icon appears only where deletion is permitted — your own comments for everyone, any comment for project owners, never a collaborator's view of someone else's comment.

### Routines

Routines are recurring tasks managed on `/app/proyectos/[id]/rutinas`. A routine defines a name, description, cost, assignee, and a schedule — no status and no priority. The schedule is captured in a two-step form (details, then scheduling) and supports two recurrences: `daily` (an "every N days" interval, with no day selection) and `weekly` (toggled weekdays combined with an "every N weeks" interval). Each routine optionally stores a perform-at time (HH:MM) — left empty, instances get no due date — and an optional start/end date range bounding occurrences. Common routines can be started from static templates (irrigation, fertilization, pest monitoring, weeding, harvest) that pre-fill name, description, recurrence, interval, and selected days.

Creation and completion drive a spawning loop. Creating a routine immediately spawns its first task instance scheduled for the next occurrence, no earlier than the start date. Marking an instance done or cancelled spawns the next instance after the completed one, scheduled with status `todo` and no priority, carrying the routine's name, description, cost, and assignee — prepended to the task table with a "next occurrence created" toast. No spawn happens when an open instance already exists (open means status is neither `done` nor `cancelled`) or when the next occurrence would fall after the end date. Routine instances carry `due_date`, are identified by a `routineId`, and show a "Routine" badge plus their due date in the Due Date column of the Tasks and My Tasks tables.

Validation is strict at creation and relaxed at edit. On create: a start date in the past is rejected ("start date cannot be in the past"), an end date not in the future is rejected ("end date must be in the future"), an end date before the start date is rejected ("end date must be after start date"), and a weekly recurrence with no day selected is rejected ("select at least one day"). On edit, only the end-after-start consistency check remains — an existing routine whose start date has passed or whose end date has passed saves fine if those dates are unchanged.

Routine data operations live in `actions/routines.ts` with schemas in `actions/schemas/routine.ts`: `RoutineSchema` for create-time refinement, `CreateRoutineSchema`/`UpdateRoutineSchema` extending it with `projectId`/`routineId`, and `DeleteRoutineSchema`. The subpage query `getProjectRoutines` is a `projectScopedAction` with `permission: projects:view` and input `{ projectId }`. `createRoutine` and `updateRoutine` share one `ROUTINE_EDIT_METADATA` (`permission: projects:edit`, `revalidate: ["/app/proyectos/:projectId"]`), and `deleteRoutine` declares `permission: projects:delete` with the same revalidation. Membership is not ownership: every mutation runs a shared `requireProjectOwner` guard that returns `FORBIDDEN` via `returnActionError` when `ctx.isProjectOwner` is false, so a collaborator holding the global `projects:edit` permission is still rejected. Create and update map validated fields through one shared `routineValues` helper (empty optional strings collapse to `NULL`) so insert and update cannot drift, and return `NOT_FOUND` when no row matches. `deleteRoutine` deliberately does not check existence — a routine deleted from another tab must still settle as success so the optimistic row can be dropped. Failures are codes via `returnActionError` (`UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION_FAILED`, declared in `actions/error-codes.ts`, translated from `errors`), never interpolated strings; the client form validates the same schema, so a server-side validation failure reaches `useSettle` as `validationErrors` and is rendered by the form rather than toasted.

Spawning goes through `createNextRoutineTask`, a `sessionAction` with empty metadata and input `SpawnRoutineTaskSchema` (`routineId`, optional `after` date), called server-to-server from `createRoutine` and `updateTaskStatus`. The routine's own project — not a caller-supplied one — decides access, and only its owners may spawn: `NOT_FOUND` for a missing routine, `FORBIDDEN` for a caller without owner access to that project, including a routine belonging to a project the caller does not own. It declares no `revalidate` metadata because both callers already revalidate the project page, and it returns `{ spawned: false }` when an open instance exists or the next occurrence falls after the end date, `{ spawned: true, task }` otherwise — callers merge `task` only when `spawned` is true.

The subpage holds its routines in a page-scoped optimistic store supplied by `RoutinesProvider` (`app/app/proyectos/[id]/rutinas/page.tsx`). `RoutinesView` (`components/projects/routines/routines-view.tsx`) reads `useRoutinesState()` and mutates through `useRoutinesActions()`, which exposes separate `createRoutine`, `updateRoutine`, and `deleteRoutine` handlers — no combined save handler — each running through `useOptimisticAction`, carrying the assignee label the optimistic row resolved into the `replaceTemp` commit (the mutations return the bare routine row, so the join cannot supply it), and settling through `useSettle`. Create and update return `void`, because no caller reads their outcome. Dialog and form state stay local to the view, which branches on its local `editingRoutine` and never imports the server actions directly. Every create, edit, and delete applies optimistically and reverts automatically on rejection, with the error toast.

Deleting a routine leaves its existing task instances in place but no longer linked to a routine.

### Expenses

Expenses live on `/app/proyectos/[id]/gastos`. The subpage shows a budget progress card — total spend (expense amounts plus task costs) compared against the project budget, a percentage bar, and a red over-budget indicator when the total exceeds it — and a table of expense rows and task cost rows ordered by date (expense `expense_date`, task creation date). Expense rows show description, a category badge translated via `categoryNames.*`, amount, and date; task cost rows show a "Task" badge and the task creation date. Both use the `YYYY-MM-DD` display format, and the table shows a combined total. Owners manage expenses through `expenses:create`, `expenses:edit`, and `expenses:delete` permissions or project ownership rights, and can edit or delete task cost rows from the same table — the task dialog opens pre-filled, or the task is deleted.

The subpage holds expenses in a page-scoped optimistic store from `ExpensesProvider` (`app/app/proyectos/[id]/gastos/page.tsx`) and lists/edits task cost rows through a `ProjectTasksProvider` mounted alongside it, nested inside `ExpensesProvider`, so the expense table reuses the project tasks store rather than a local reducer. `ProjectExpenses` (`components/projects/expenses/project-expenses.tsx`) reads `useExpensesState()` and `useProjectTasksState()` and mutates through `useExpensesActions()` and `useProjectTasksActions()` — it owns no `useReducer` for either list. Every expense create, edit, and delete applies optimistically and reverts automatically on rejection; delete shows a success toast and restores the row if the server refuses. Because the create/update actions return the bare expense row without its joined category name, the category badge on an optimistic row is resolved from the categories the page passes in.

### My Tasks

The My Tasks page at `/app/mis-tareas` gathers every task assigned to the current user across projects, reachable from the sidebar's "My Tasks" item. It requires `projects:view` — a user without it gets a 403 forbidden screen, no server error. Tasks are held in a page-scoped store: `MyTasksProvider` mounted by `app/app/mis-tareas/page.tsx`, seeded from `getMyTasks({})`.

Each row shows task name, project name formatted as "Project (Owner)" for owner context, status, cost, comment count, and a Due Date column with the due date and time when set; routine-spawned tasks carry a "Routine" badge. Overdue works as on the project table: a "Overdue" badge with red due-date text for tasks not `done` or `cancelled` whose due date has passed, and nothing for cancelled tasks, which render as a read-only badge with no status dropdown. Assignees change their own status optimistically from the inline dropdown — with collaborator-level restrictions (`in_progress`, `blocked`, `in_review`, never `done` or `cancelled`) — with the global loading indicator and a success toast. Double-clicking a row or clicking the comment count opens the same comments panel, backed by the my-tasks store.

Status and project filters are client-side projections over the full task set already in the store, not separate queries — filtering makes no server request. Filter selection is local UI state and never lives in the store, which always holds the full set, so a refresh can reseed without contradicting an active filter. The status filter includes "Cancelled". Because `useRefreshOnFocus` triggers `router.refresh()` when the window regains focus, tasks completed elsewhere appear with their new status after the store reseeds, without a full page reload. When a status change returns a routine's `nextTask`, merging it preserves the completed task's existing comment count rather than resetting it, and the new task's visibility under the current filter is derived from the projection.

### Visibility and categories

Project queries are user-scoped: owners see only the projects they own, collaborators do not see them in the list at all, and admins and super users see everything. Project and expense category names resolve via i18n in the `categoryNames` namespace keyed by slug with fallback to the DB name — on project cards, the details subpage category label, and expense table badges (category CRUD and schema live in the category-management capability).

## Non-goals

- Collaborator access to project details. Collaborators comment on tasks through their assignments but cannot see project subpages or the project in the list.
- Color uniqueness across projects. The palette is fixed at 6 and reuse is explicitly allowed.
- Global-permission-based authorization for membership changes. Ownership on the project is the guard, intentionally stricter than super-user access.
- A non-optimistic path for any list or membership mutation. Stores are seeded once per mount, so every change commits or discards through optimistic actions.
- Prop-threaded project context. Components read `useProjectContextState()`; `ProjectView` takes no `projectId` or `context`.
- Server-side or prop-drilled comment counts. The count moves inside the same store action as the comment.
