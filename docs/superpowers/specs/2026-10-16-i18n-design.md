# Internationalization — Design

## Why this exists

The app serves both English- and Spanish-speaking users, and it should open in the language a user expects without a per-visit decision. The locale is resolved once per request from the most authoritative signal available — a cookie if the user has chosen before, otherwise the browser's `Accept-Language` header — and falls back to a default so the UI is never left untranslated. The same resolution is available to server actions, which need to produce error messages in the user's language even though they run away from the React tree.

Two surfaces have to agree on the language: the rendered UI and the errors that come back from actions. If actions returned English codes while the page rendered Spanish, the mismatch would show up exactly when something goes wrong, which is the worst time. The design therefore routes both through the same locale resolution and treats action error codes as translation keys.

## Goals

- Resolve the locale from the `NEXT_LOCALE` cookie, then `Accept-Language`, then a default.
- Provide a locale switcher in the user nav dropdown for English and Spanish.
- Translate all UI text and all server-action error codes.
- Give server actions a shared helper for locale-aware messages.

## Design

### Locale detection

The resolved locale comes from a cookie first, falling back to the browser's `Accept-Language` header, and finally to a default locale. A returning user with the `NEXT_LOCALE` cookie set to `"en"` sees English on every page, ahead of anything the browser advertises. A first-time visitor with no cookie is matched against their `Accept-Language` header: a header of `fr-CH, fr;q=0.9, en;q=0.8` resolves to French via the closest supported match. When there is no match at all — a visitor sending `ja;q=1`, for instance — the UI falls back to Spanish, the default locale.

### Locale switcher

The switcher lives in the user nav dropdown and toggles between English and Spanish. Clicking it from English switches the locale to Spanish, updates all UI text, and writes the `NEXT_LOCALE` cookie so the choice persists. The control reflects the current state by presenting the alternative: with English active, it shows "ES" as the option.

### Translated UI

Every UI component renders its text in the resolved locale, across all supported namespaces. On the reports page in Spanish, chart labels read "Producto" and "Servicio" and empty states read "No hay datos de ingresos aún." Server-action errors are translated too: when a server action fails with a validation error under a Spanish locale, the message is displayed in Spanish.

Safe-action error codes are translated by construction. When a safe action returns a `serverError` with code `ALREADY_OWNER`, the client renders it through `useActionError`, which reads the message from `errors.ALREADY_OWNER`. Every code in `ActionError` (`actions/error-codes.ts`) has a message in each supported locale, so a code can never surface untranslated.

### Server action translation

Server actions get their translations from a shared helper rather than resolving the locale themselves. A server action imports `getActionT` from `lib/util/i18n-actions.ts`; calling `getActionT('actions.clients')` returns a function that translates keys from the `actions.clients` namespace, with the locale resolved from the `NEXT_LOCALE` cookie. This keeps action messages consistent with the UI and avoids duplicating locale detection per action.

## Non-goals

- More than two locales. The switcher toggles between English and Spanish, and Spanish is the default.
- Locale in the URL. Language is carried by the cookie and header, not by a path segment.
